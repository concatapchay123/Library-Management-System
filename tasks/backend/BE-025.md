# BE-025 — In-app notification persistence and read workflow

## Task information

- Owner: Backend
- Status: Planned
- Priority: P2

## Outcome

Persist tenant-scoped in-app notifications from durable domain events and let authorized users read or mark them read.

## Dependencies

- BE-024
- BE-015

## Interfaces and source of truth

- Consumes: durable dispatcher from BE-015 and event-producing circulation/payment workflows.
- Produces: core.notifications, notification consumer and notification read API.

## In scope

- Migrate notification records with delivery/read state and tenant constraints.
- Consume versioned loan, reservation, overdue and payment events idempotently.
- Implement notification listing and read-state mutation with authorization.

## Out of scope

- Email provider delivery, UI inbox, push notifications and a second outbox protocol.

## Test-first sequence

1. Add backend/tests/integration/core/test_notifications.py for event replay, unread listing and read-state transition.
2. Run: cd backend; python -m pytest tests/integration/core/test_notifications.py -q. Record the missing notification-consumer failure.
3. Implement notification migration, consumer, service, contract and API adapters.
4. Run the focused integration test and dispatcher replay test.

## Evidence checkpoint

- Replayed domain event creates no duplicate notification.
- One user cannot read or mutate another tenant notification.

## Acceptance criteria

- Notification read-state transitions are explicit and idempotent.
- Payloads exclude secrets and payment credentials.
- The implementation reuses BE-015 dispatcher semantics.

## Reviewer checklist

- Notification event types are versioned.
- No notification mutation bypasses authorization or tenant context.
