# BE-017 — Concurrent checkout locking and idempotency replay

## Task information

- Owner: Backend
- Status: Completed
- Priority: P1

## Outcome

Guarantee that one copy cannot receive competing active loans and that retrying a write request does not duplicate its side effects.

## Dependencies

- BE-016

## Interfaces and source of truth

- Consumes: checkout service from BE-016 and idempotency requirements in docs/api-design.md.
- Produces: transaction-locking protocol, idempotency record and 24-hour retention behavior.

## In scope

- Lock the physical copy within the checkout transaction.
- Persist idempotency key, request hash and original response for checkout/return.
- Reject reuse of one key with a different payload and expire safe records after 24 hours.

## Out of scope

- Reservation allocation, provider-payment idempotency and generic event consumer deduplication.

## Test-first sequence

1. Add backend/tests/integration/core/test_checkout_concurrency.py for two concurrent checkouts and repeated idempotency requests.
2. Run: cd backend; python -m pytest tests/integration/core/test_checkout_concurrency.py -q. Record the race/replay failure.
3. Implement database locking, idempotency persistence and response replay.
4. Run the focused integration test against SQL Server.

## Evidence checkpoint

- Two simultaneous checkout attempts for one copy yield one success and one documented conflict.
- A repeated key returns the original result with no duplicate audit/outbox row.

## Acceptance criteria

- No check-then-insert race remains for active checkout.
- Idempotency data contains no raw refresh token, card payload or uncontrolled PII.
- Expired records no longer suppress a valid new request.

## Reviewer checklist

- [x] Lock scope is limited to the copy and transaction.
- [x] Request-hash mismatch is explicit and auditable.

### 2. Physical Copy Locking Protocol

- Executed atomically inside the active checkout transaction before copy availability check in `LoanService.checkout_loan`.

### 3. Idempotency Key Persistence & Response Replay
- Schema migration `backend/migrations/versions/0013_idempotency_keys.py`:
  - `ops.idempotency_keys` table with primary key `key_id`, foreign key `organization_id`, unique constraint `(organization_id, idempotency_key, method, endpoint)`.
  - Expiration index `IX_ops_idempotency_keys_tenant_expires`.
  - Strict RLS filter and block predicates (`AFTER INSERT`, `AFTER UPDATE`, `BEFORE DELETE`).
- Application & Store layers:
  - Deterministic canonical request hashing (SHA-256).
  - Strict sensitive key rejection (`validate_safe_response` rejects tokens, passwords, secrets, card data).
  - 24-hour expiration lifecycle: expired keys are pruned/overwritten and do not suppress valid new requests.
  - Replay response injects `Idempotency-Replayed: true` header and returns original status and body without duplicate transaction execution.
  - Key reuse with conflicting payload raises `IdempotencyConflictError` (409 Conflict Problem Details) and emits `idempotency.request_hash_mismatch` audit event.
