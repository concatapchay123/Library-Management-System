# BE-010 — Data-driven RBAC and authorization service

## Task information

- Owner: Backend
- Status: Planned
- Priority: P0

## Outcome

Authorize protected use cases through tenant-scoped role and permission data rather than hard-coded role names.

## Dependencies

- BE-008
- BE-005

## Interfaces and source of truth

- Consumes: protected principal from BE-008 and API permission matrix in docs/api-design.md.
- Produces: roles, permissions, user-role and role-permission persistence plus application authorization port.

## In scope

- Migrate tenant-scoped RBAC relations with composite foreign keys and RLS policies.
- Implement assignment, revocation and effective-permission evaluation.
- Enforce permission decisions at the application-service boundary and audit RBAC mutations.

## Out of scope

- Organization settings, catalog permissions, frontend navigation hiding and platform-control operations.

## Test-first sequence

1. Add backend/tests/api/core/test_rbac.py for assignment, revocation and authorization matrix denial.
2. Run: cd backend; python -m pytest tests/api/core/test_rbac.py -q. Record the missing authorization-port failure.
3. Implement RBAC persistence, service operations and API adapters.
4. Run the focused API test and RBAC migration integration test.

## Evidence checkpoint

- A permission change takes effect without a code deployment.
- Unauthorized requests return a stable authorization failure without data leakage.

## Acceptance criteria

- Services request named permissions through one authorization port.
- No protected behavior relies on a hard-coded role name.
- RBAC mutations produce tenant-scoped audit records.

## Reviewer checklist

- Route permission checks do not replace service ownership checks.
- All RBAC tenant tables have RLS and composite tenant constraints at creation.
