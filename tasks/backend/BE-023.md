# BE-023 — Fine calculation, invoices and immutable allocations

## Task information

- Owner: Backend
- Status: Completed
- Priority: P2

## Outcome

Assess public-library fines and issue immutable invoices with allocation rules that preserve financial integrity.

## Dependencies

- BE-022
- BE-005

## Interfaces and source of truth

- Consumes: member/subscription records from BE-022 and audit/outbox transaction contract from BE-005.
- Produces: fines, invoices, invoice lines and allocation service using decimal money values.

## In scope

- Migrate fines, invoices, invoice lines and allocation records with explicit currency and decimal(19,4) values.
- Implement fine assessment and immutable issued invoices.
- Enforce allocation totals that cannot exceed their related fine or payment amount.

## Out of scope

- Payment-provider callbacks, reconciliation, general ledger and frontend payment entry.

2. Run: cd backend; python -m pytest tests/integration/public_library/test_fines_invoices.py -q. Record the missing finance-service failure.
3. Implement migrations, money value types, services, contracts and API adapters.
4. Run the focused integration test and audit/outbox test.

- Over-allocation and floating-point money paths are rejected.

## Acceptance criteria

- Currency is explicit for every money amount.
- Financial transitions are auditable and tenant isolated.
- Fine calculation is independent from a browser or payment provider callback.

### 2. Evidence Checkpoint Validation

- **Issued invoice lines and totals cannot be changed:**
  - Validated by `test_invoice_immutability` in `test_fines_invoices.py` and `test_issue_invoice_endpoint_and_immutability` in `test_fines_invoices_api.py`.
  - Service methods `modify_invoice_lines` and `update_invoice_total` unconditionally raise `InvoiceImmutableError` once an invoice is issued.
  - HTTP `PUT /api/v1/public-library/invoices/{invoice_id}/lines` and `PATCH /api/v1/public-library/invoices/{invoice_id}` reject attempts with HTTP 409 Conflict Problem Details.
- **Over-allocation and floating-point money paths are rejected:**
  - Validated by `test_money_rejects_floating_point`, `test_fine_assessment_rejects_floating_point`, `test_allocation_caps_and_over_allocation_rejected`, `test_assess_fine_endpoint_rejects_floating_point`, `test_calculate_overdue_fine_endpoint`, and `test_allocation_rejects_floating_point`.
  - Passing `float` to `Money`, fine creation, overdue calculation, or payment allocation raises `TypeError` with message `"Floating-point money amounts are rejected; use Decimal instead."`
  - HTTP endpoints reject float inputs with HTTP 400 Bad Request Problem Details before reaching domain logic.
  - Allocations cannot exceed either the remaining unallocated balance of the fine or the remaining unallocated balance of the payment, raising `OverAllocationError` (HTTP 409 Conflict).
- **Pure Decimal arithmetic end to end:**
  - Database schema defines `decimal(19,4)` for `fines.amount`, `payments.amount`, `invoices.subtotal`, `invoices.tax`, `invoices.total`, `invoice_lines.unit_price`, `invoice_lines.amount`, and `payment_allocations.amount`.
  - Domain value object `Money` uses `Decimal("0.0001")` quantization and Decimal arithmetic exclusively.
- **Explicit currency:**
  - Currency is verified using regex `^[A-Z]{3}$` and required on all money creations. Currency mismatches between payments and fines during allocation raise `CurrencyMismatchError` (HTTP 422).
- **Auditable and tenant isolated:**
  - Financial operations (`fine.assessed`, `fine.waived`, `invoice.issued`, `invoice.voided`, `payment.recorded`, `payment.allocated`) execute via `AuditedTransaction` emitting transactional `AuditEvent` and `OutboxEvent` records matching the BE-005 contract.
  - All tables enforce `organization_id NOT NULL`, composite tenant unique/foreign keys, and SQL Server Row-Level Security filter/block predicates.
- **Independent fine calculation:**
  - Pure calculation function `calculate_overdue_fine` computes fines strictly from calendar duration (`due_at`, `effective_return_at`), `daily_rate`, and optional `max_fine`, independent of any payment processor or client callback.
- **No general ledger added:**
  - All financial tracking is scoped strictly to domain tables `fines`, `invoices`, `invoice_lines`, `payments`, and `payment_allocations`.

### 3. Architecture & Separation of Concerns

- **Domain Layer (`openlibrary.modules.public_library.domain`):**
  - Value object `Money` with Decimal precision, explicit currency validation, and float rejection.
  - Immutable domain entities: `Fine`, `InvoiceLine`, `Invoice`, `Payment`, `PaymentAllocation`.
  - Domain rule functions: `calculate_overdue_fine`.
  - Domain exceptions: `InvalidMoneyError`, `CurrencyMismatchError`, `InvoiceImmutableError`, `OverAllocationError`, `FineAlreadyClosedError`, etc.
- **Application Layer (`openlibrary.modules.public_library.application`):**
  - Protocol `PublicLibraryStore` extended with fine, invoice, payment, and allocation persistence contracts.
  - `PublicLibraryFinanceService` implementing finance use cases with RBAC enforcement (`public_library.read`, `public_library.manage`), edition enablement validation, and transactional audit/outbox execution.
- **Infrastructure Layer (`openlibrary.modules.public_library.infrastructure`):**
  - `SqlServerPublicLibraryStore` implementing parameterized queries (`sqlalchemy.text`), row mapping to domain dataclasses with Decimal conversions, and tenant isolation.
- **API Adapter Layer (`openlibrary.modules.public_library.api`):**
  - Endpoints for `/fines`, `/fines/{id}`, `/fines/calculate`, `/fines/{id}/waive`, `/fines/{id}/allocations`, `/invoices`, `/invoices/{id}`, `/invoices/{id}/void`, `/payments`, `/payments/{id}`, `/payments/{id}/allocations`, `/allocations`, and `/allocations/{id}`.
  - Strict input sanitization with `_parse_decimal` rejecting numeric floats and formatting responses to RFC 7807 problem details.
- **Runtime Composition (`openlibrary.app.runtime`, `openlibrary.app.factory`, `openlibrary.app.config`):**
  - Wired `PublicLibraryFinanceService` with `SqlServerAuditedTransaction` and tenant connection provider into `AppConfig` and `create_public_library_blueprint`.
- **Database Migration (`backend/migrations/versions/0017_public_library_fines_invoices.py`):**
  - Creates tables in `public_library` schema with `decimal(19,4)` amounts, composite tenant constraints, and RLS predicates attached to `core.organization_tenant_policy`.
- **Contract & OpenAPI Specification (`contracts/openapi/v1.yaml`):**
  - Published 18 new schemas and 13 new path operations for all public library financial resources.
