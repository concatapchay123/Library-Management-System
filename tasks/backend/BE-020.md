# BE-020 — Education entities and tenant-scoped relations

## Task information

- Owner: Backend
- Status: Completed
- Priority: P2

## Outcome

Provide education-domain records for students, teachers, departments, classes, courses, semesters and memberships.

## Dependencies

- BE-011
- BE-006

## Interfaces and source of truth

- Consumes: tenant boundary from BE-011 and extension API rules in docs/api-design.md.
- Produces: education schema, repositories and protected education resource endpoints.

## In scope

- Migrate education entities with tenant-scoped identifiers, composite relations and RLS policies.
- Validate semester dates and enrollment relations.
- Add authorization-protected contracts and API adapters for education data.

## Out of scope

- Borrowing policy selection, loan snapshots, education frontend screens and public-library membership.

## Test-first sequence

1. Add backend/tests/integration/education/test_entities.py for tenant isolation, date validation and relationship constraints.
2. Run: cd backend; python -m pytest tests/integration/education/test_entities.py -q. Record the absent education-module failure.
3. Implement migrations, repositories, application services, contract and API adapters.
4. Run the focused integration test and tenant catalog verifier.

## Evidence checkpoint

- Cross-tenant student and teacher access is rejected by authorization and RLS.
- Invalid semester date ranges are rejected before persistence.

## Acceptance criteria

- Student and teacher identifiers are unique only within their organization.
- Every education relation has a tenant-safe composite foreign key.
- Education APIs are unavailable when the edition is disabled for an organization.

## Reviewer checklist

- Core domain imports no education implementation.
- Schema and API names match docs/database-design.md and docs/api-design.md.

### 2. Tenant Catalog Verification & Constraints
- Database migration `backend/migrations/versions/0015_education_entities.py`:
  - 8 tables created under `education` schema: `departments`, `semesters`, `courses`, `classes`, `students`, `teachers`, `class_memberships`, `borrower_policies`.
  - All foreign keys include `(organization_id, ...)` as composite FKs.
  - Fail-closed RLS filter predicate `core.tenant_access_predicate(organization_id)` and block predicates (`AFTER INSERT`, `AFTER UPDATE`, `BEFORE DELETE`) added to `core.organization_tenant_policy` for all 8 tables.
  - Check constraints for semester dates (`starts_on < ends_on`) and membership dates (`left_at IS NULL OR left_at >= joined_at`).
  - Verified by `openlibrary.modules.core.infrastructure.tenancy.verify_tenant_catalog` against active SQL Server instance.

### 3. Domain, Application, and API Implementation
- Clean architecture separation:
  - Domain: `openlibrary.modules.education.domain` declares pure dataclasses and business exceptions (`InvalidSemesterDates`, `InvalidMembershipDates`, `DuplicateIdentifierError`, `ProfileAlreadyExistsError`, `EditionUnavailableError`).
  - Application: `EducationService` enforces `education.read` and `education.manage` permissions, verifies edition enablement via `is_edition_enabled`, and handles CRUD operations.
  - Infrastructure: `SqlServerEducationStore` executes parameterized queries within `SqlServerTenantContext`.
  - API: `create_education_blueprint` registers routes under `/api/v1/education` and `/education`, mapping domain exceptions to RFC 7807 Problem Details.
  - Wiring: Integrated into `AppConfig`, `create_app`, and runtime dependencies in `openlibrary.app`.
  - Zero imports of education module inside core domain.
