# BE-026 — Email delivery consumer, bounded retry and worker observability

## Task information

- Owner: Backend
- Status: Planned
- Priority: P2

## Outcome

Deliver notification emails through a replaceable adapter with replay-safe retry and operational visibility.

## Dependencies

- BE-025
- BE-015

## Interfaces and source of truth

- Consumes: notification events from BE-025 and dispatcher/job contract from BE-015.
- Produces: email port, development sink, email delivery consumer, worker readiness and queue metrics.

## In scope

- Define email adapter interface and a development sink.
- Implement idempotent email consumer with bounded exponential retry and dead-letter visibility.
- Expose worker health, attempts, last error and queue/dead-letter metrics.

## Out of scope

- A mandated production email vendor, browser inbox, unbounded retry and changing source transaction outcomes.

## Test-first sequence

1. Add backend/tests/integration/ops/test_email_delivery.py for provider failure, retry, replay and dead-letter behavior.
2. Run: cd backend; python -m pytest tests/integration/ops/test_email_delivery.py -q. Record the missing email-consumer failure.
3. Implement the adapter port, sink, consumer, metrics and worker health endpoint.
4. Run the focused integration test and dispatcher suite.

## Evidence checkpoint

- A provider failure does not roll back the originating loan or payment transaction.
- Failed jobs expose bounded attempts and actionable last-error metadata.

## Acceptance criteria

- Development delivery is deterministic without external provider credentials.
- Worker reconnect and graceful shutdown are test-covered.
- Email payloads are replay-safe and contain no credential material.

## Reviewer checklist

- No unbounded retry loop exists.
- A domain handler does not create a parallel queue or outbox protocol.
