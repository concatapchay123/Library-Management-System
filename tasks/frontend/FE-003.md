# FE-003 — Login, refresh session and protected-route behavior

## Task information

- Owner: Frontend
- Status: Planned
- Priority: P2

## Outcome

Let users authenticate with organization slug and manage browser session recovery without persistent access-token storage.

## Dependencies

- FE-002

## Interfaces and source of truth

- Consumes: auth endpoints in contracts/openapi/v1.yaml and shared controls from FE-002.
- Produces: login form, in-memory access-token state, refresh flow and protected-route guard.

## In scope

- Implement organization_slug, email and password login fields in familiar order.
- Keep access tokens only in memory and use the HttpOnly refresh cookie through the documented refresh endpoint.
- Redirect protected routes after session failure and display the uniform safe authentication message.

## Out of scope

- Password-reset UI, role management, localStorage/sessionStorage token persistence and client-side permission enforcement.

## Test-first sequence

1. Add frontend/tests/features/auth/auth-flow.test.tsx for protected redirect, successful refresh and refresh failure reset.
2. Run: cd frontend; npm run test -- --run tests/features/auth/auth-flow.test.tsx. Record the missing auth-flow failure.
3. Implement login, session provider and protected-route guard.
4. Run the focused test, npm run typecheck, npm run lint and npm run build.

## Evidence checkpoint

- Wrong slug and wrong password render the same safe message.
- Refresh failure clears in-memory state and redirects to login.

## Acceptance criteria

- Login submits organization_slug exactly as required by the API contract.
- Access token is never written to browser persistent storage.
- A valid refresh session restores protected-route access without a second login form submission.

## Reviewer checklist

- Client-side route guard is not treated as an authorization boundary.
- Authentication error UI does not reveal whether an account or organization exists.
