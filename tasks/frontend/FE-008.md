# FE-008 — Reservation status and notification inbox

## Task information

- Owner: Frontend
- Status: Planned
- Priority: P2

## Outcome

Show users their reservation progression and time-sensitive notifications in one concise inbox.

## Dependencies

- FE-007

## Interfaces and source of truth

- Consumes: reservation endpoints from BE-018 and notification endpoints from BE-025.
- Produces: reservation status route, notification inbox and read-state interaction.

## In scope

- Render reservation queue/hold status using backend-provided state and dates.
- Present notification list, unread/read distinction and mark-read operation.
- Provide empty, loading and failure states with one clear next action.

## Out of scope

- Email delivery configuration, queue reordering, push notifications and client-side hold-expiry calculation.

## Test-first sequence

1. Add frontend/tests/features/inbox/reservation-inbox.test.tsx for hold display, notification read transition and empty inbox.
2. Run: cd frontend; npm run test -- --run tests/features/inbox/reservation-inbox.test.tsx. Record the missing inbox failure.
3. Implement reservation and notification routes using typed data.
4. Run the focused test, npm run typecheck, npm run lint and npm run build.

## Evidence checkpoint

- Marking a notification read updates only after a successful server response.
- No-reservation and no-notification states use distinct, understandable copy.

## Acceptance criteria

- Reservation status does not promise a pickup or allocation beyond server facts.
- Inbox contains one dominant action: open the relevant record.
- Read-state controls are keyboard accessible.

## Reviewer checklist

- UI does not expose another user's notification or reservation data.
- Notifications are not treated as a source of authorization truth.
