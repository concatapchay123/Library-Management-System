# FE-004 — Typed API client, Problem Details and common request states

## Task information

- Owner: Frontend
- Status: Planned
- Priority: P2

## Outcome

Centralize typed contract access and make loading, empty, error and request-correlation states understandable before feature screens are added.

## Dependencies

- FE-003

## Interfaces and source of truth

- Consumes: contracts/openapi/v1.yaml and authenticated session state from FE-003.
- Produces: typed API client, Problem Details renderer, request-state components and request_id support display.

## In scope

- Generate or implement one typed API client from OpenAPI.
- Normalize RFC Problem Details into concise user messages with a visible support request_id.
- Add reusable loading, empty, retry and non-destructive error states.

## Out of scope

- Duplicated endpoint string literals in feature code, domain-policy evaluation and feature-specific screens.

## Test-first sequence

1. Add frontend/tests/shared/api-client.test.ts for typed request serialization and Problem Details mapping.
2. Run: cd frontend; npm run test -- --run tests/shared/api-client.test.ts. Record the missing API-client failure.
3. Implement client, error mapping and common request-state components.
4. Run the focused test, npm run typecheck, npm run lint and npm run build.

## Evidence checkpoint

- One documented Problem Details sample renders title, helpful action and request_id.
- Feature modules import the client rather than assembling endpoint strings.

## Acceptance criteria

- User-facing errors are concise and do not expose SQL, stack traces or token data.
- Empty states state what is absent and the one next action when one is permitted.
- Retry controls repeat only safe documented requests.

## Reviewer checklist

- API types remain derived from the versioned contract.
- Client error normalization never changes backend authorization or money decisions.
